## Главные выводы

- **Права доступа построены правильно.** Ни одна роль не попадает туда, куда не должна, это доказано матрицей.
- **Слабое место — пароли.** Нет блокировки перебора, нет правил сложности, нет смены пароля. По отдельности это неудобства, вместе — реальный риск: пароль `11111111` подбирается перебором без ограничений.
- **Найдено противоречие в правилах.** Запись на курс открыта персоналу, из-за чего чужой преподаватель видит уроки, но не квиз.

## Решения для встречи (D1–D6)

1. Блокировка: 5 попыток за 15 минут → 429 на 15 минут.
2. Пароль: ≥ 8, буква + цифра, не равен email.
3. Смена пароля завершает остальные сессии.
4. Персонал не записывается на курсы.
5. Убрать старые `/api/demo/*`.
6. Восстановление пароля по email — вне объёма.

Вероятные вопросы:
- *Почему одинаковый ответ на неверный пароль и несуществующий email?* Иначе по ответу можно узнать, у кого есть аккаунт. Время ответа тоже одинаковое: хеш считается и для несуществующего email.
- *Зачем хранить хеш токена, а не сам токен?* Если таблица сессий утечёт, войти по ней нельзя.
- *Почему блокировка по email, а не по IP?* Атакуют конкретный аккаунт; IP легко меняется. Попытки на несуществующий email тоже считаются, иначе блокировка выдаст, что аккаунт есть.
- *Почему смена роли действует сразу?* Роль не хранится в cookie, а читается из БД при каждом запросе.
- *Что такое xfail?* Тест записывает требование, которое ещё не выполнено. CI зелёный, а когда задание сделают, тест сам сообщит, что пометку пора снять.
