# План проверок БД Руслана

Исходная задача: optimization errors and test report. Цель — доказательства на текущем скелете, без вымышленных дефектов и ускорений. PostgreSQL обязателен; SQLite не подменяет проверки PostgreSQL.

| ID | Проверка | Ожидание |
|---|---|---|
| DBT-01 | upgrade на пустой mini_lms_test_* | roles/users/user_profiles и alembic_version |
| DBT-02 | alembic check | отличий моделей и схемы нет |
| DBT-03 | seed дважды | 3 демо-пользователя, 3 роли, 3 профиля без дублей |
| DBT-04 | повторный email | IntegrityError, транзакция откатывается |
| DBT-05 | неизвестная роль | FK запрещает запись |
| DBT-06 | пустое имя, email с uppercase, неизвестная роль name | CHECK запрещает запись |
| DBT-07 | удаление пользователя | его профиль удалён, остальные записи целы |
| DBT-08 | downgrade base / upgrade head | откат и повторное применение успешны на одноразовой БД |
| DBT-09 | запрос по email и отчёт ролей | корректные строки и EXPLAIN ANALYZE BUFFERS |
| DBT-10 | сравнение производительности | при реальной проблеме: одинаковые данные и запрос до/после, несколько замеров |

Автоматические проверки DBT-03–07 — backend/tests/test_database.py. Подготовка и DBT-01/02/08 — DB_WORKFLOW.md. DBT-09 — database/queries/account_checks.sql. DBT-10 не имеет смысла доказывать на трёх демо-строках.

Для замеров фиксировать PostgreSQL, число строк, запрос, параметры, число повторов, медиану времени, план и BUFFERS. Влияние прогрева учитывать отдельно. Не вводить искусственный плохой индекс только ради красивого отчёта.
